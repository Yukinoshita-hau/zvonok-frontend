# Windows Desktop development and release contract

## Development

- `npm run dev:desktop`: stable renderer/main/preload; reload is manual. `npm run dev:desktop:hmr` explicitly enables Vite renderer HMR for test calls. Dev profile is `%APPDATA%/Zvonok-development`, separate from installed Zvonok. `ZVONOK_DESKTOP_PROFILE` can select an isolated absolute test directory; never select a production profile for QA.
- `npm run dev:desktop:watch`: explicit opt-in to compile/restart main and preload on changes. Restart ends active media. Use test calls only; this command prints that warning. Renderer Fast Refresh can also remount media when its owner module changes. Do not use this workflow for a real call whose continuity matters.
- `npm run build`: production web frontend and TypeScript. `npm run build:electron`: main/CJS preloads only, not native acceptance.
- `npm run pack:desktop`: local bundled UI + win-unpacked directory. `npm run dist:desktop`: local installer; both use `--publish never`. Neither is production distribution authorization.
- Dev renderer accepts loopback HTTP only; `VITE_DEV_SERVER_URL` is ignored by packaged app. Production uses bundled `dist/index.html` and HashRouter. Backend deployments remain separate and must preserve API compatibility.

Do not run load/FPS campaigns concurrently with Electron performance acceptance. Generated test profiles/packages under `work/electron-native` are excluded from Vite watchers to prevent Windows SQLite `EBUSY` crashes. Test profiles and generated packages are gitignored.

Desktop packaging validates explicit `VITE_API_URL` (HTTPS), `VITE_LIVEKIT_URL` (WSS) and optional `VITE_WS_URL` (WSS) before building. LiveKit signaling and its HTTP validation counterpart must be included even when LiveKit uses a different host or port from Core. The configured LiveKit URL must match the server URL returned by Core. The checkout `.env` targets loopback HTTP/WS for development; it must not silently become production configuration. For an isolated local QA package explicitly set `ZVONOK_DESKTOP_STAGING=1`; only loopback HTTP/WS is then allowed. This flag changes build-time CSP to include those exact origins, never all HTTP origins. It does not enable production updater installation. CSP is embedded in packaged HTML by `build:desktop-renderer`, while ordinary web/Docker build remains unchanged.

E6 acceptance reproduced file-renderer refresh failure with Lax cookies. A separate isolated None/Secure test passed; this is not authorization to change production cookies or permit arbitrary null origins. A production desktop origin, CORS/CSRF policy and origin/storage migration require security review before release.

## Updates in this checkout

Electron-builder 26.18.0 + NSIS uses electron-updater 6.8.11, not Electron's Squirrel updater. Electron was updated from 43.0.0 to 43.8.3 within the existing range after npm advisories. `npm run test:desktop:staging` exercises the real library against loopback metadata and a deliberately non-executable payload. It does not install an update or prove Authenticode.

Dev UI staging: set `ZVONOK_UPDATE_STAGING_URL=http://127.0.0.1:<port>/` before launching `dev:desktop`. Serve `latest.yml`, `.exe` and `.blockmap` generated by an isolated staging NSIS build. Only loopback HTTP is accepted in unpackaged dev. No install is permitted from dev, even after a successful SHA-512 download. Default update state is disabled without configuration. Do not use test payloads as installers.

Production remains disabled until an approved `resources/desktop-update-policy.json` is included by the signed build. Required shape (values must be agreed, not copied literally):

```json
{
  "provider": "generic",
  "url": "https://APPROVED-HOST/desktop/stable/",
  "channel": "latest",
  "publisherName": ["APPROVED AUTHENTICODE CERTIFICATE SUBJECT"],
  "updaterCacheDirName": "zvonok-desktop-updater"
}
```

This is trusted build input, never renderer/remote configuration. JSON also parses as YAML for the updater's signature configuration. The exact publisher identity is pinned by the main process; metadata/artifacts/redirects are restricted to the configured HTTPS origin. No credentials/query strings are allowed in the policy URL. Do not grant arbitrary CDN redirects or weaken certificate verification to work around hosting errors. The current v6 updater uses HTTPS + SHA-512 + Authenticode, not signed metadata. Metadata authenticity relies on the approved HTTPS origin; a compromised feed can deny service, while arbitrary unsigned binaries must still fail signature verification. Signed-manifest migration requires a separate reviewed builder/updater version change.

`autoInstallOnAppQuit=false`, no downgrade, no web installers. Check during startup and every six hours; manual check in tray/Settings. Checks/downloads never block launch. Ready update offers Later or user-approved restart. Install requires fresh renderer idle state and no active dock owner, rechecked after the confirmation. A stale/hung/crashed renderer fails closed. Stable is `latest`; a separately built approved beta policy uses `beta`. No user-controlled channel switch.

## CI/CD recommendation (not connected or published)

1. Windows runner with pinned Node/npm and locked dependencies; `npm ci`, full unit, production frontend build, Electron compilation, sequential browser regressions.
2. Assign a strictly increasing approved semantic version; `0.0.0` is not a release version. Build bundled UI, not a remote web shell.
3. Obtain approved signing certificate through protected CI credentials; force signing failure when unavailable (`forceCodeSigning:true`, `win.verifyUpdateCodeSignature:true`, agreed publisherName). Never put signing/update-access tokens into the app.
4. Include the approved policy via electron-builder `extraResources`; use matching generic HTTPS publish config and `electronUpdaterCompatibility >=2.16`. Build NSIS **without publishing** first.
5. Verify Authenticode on app and installer, inspect ASAR/preloads/fuses, reject secrets/unsafe URLs in artifacts. Test two isolated installed versions, existing auth cookie restoration, real call restart guard, hash/signature/corrupt-feed failures and power loss.
6. Approval gate: stage artifacts on a trusted HTTPS test feed; install N→N+1 on a separate Windows account/VM. Never distribute unsigned production updates.
7. After release approval, upload installer/blockmap first, immutable metadata last, preserving prior version artifacts for diagnosis. No publishing provider is configured here.
8. Roll forward with a higher version for recovery. Automatic downgrade/rollback is intentionally disabled; validate backup/recovery manually rather than promising unsupported rollback.

## Separate cookie/fuse migration gate

Read-back of the actual packaged executable found CookieEncryption OFF, RunAsNode/NodeOptions/NodeCliInspect ON, embedded ASAR validation and OnlyLoadAppFromAsar OFF. Do not equate a HttpOnly cookie with encrypted-at-rest storage. No credentials were extracted into renderer storage or safeStorage.

Cookie encryption is a one-way transition: existing plaintext cookies become encrypted on write, and a subsequent old build with the fuse disabled can no longer use that cookie database. Before enabling it: retain appId/userData identity; test old-profile → new signed app with a non-secret marker cookie and then a real isolated refresh session; verify restart/rotation/logout; test OS key access; block downgrade and document manual old-installer recovery without silently deleting profile data. Do not flip it back during rollback. Enable other production fuses in a separate signed packaging change with a dedicated non-inspector acceptance method. These migration tests were not run here. [Electron fuse contract](https://www.electronjs.org/docs/latest/tutorial/fuses).

## Bundled versus remote UI

Bundled UI gives an atomic Electron/preload/renderer version, offline startup, predictable CSP and reviewed release integrity. It costs a full signed release for UI changes. Remote UI can update faster, but requires network availability, exposes the native bridge to a mutable remote origin, and can break compatibility between the server UI and older preloads. It adds cold-start/network and operational rollback risks. Keep Zvonok bundled; backend API changes ship independently when compatible.


## E6.1: запуск и подготовленное обновление

Готовность окна определяется ready-to-show и подтверждением первого React commit через owner-validated desktop:renderer-ready; зависший второстепенный ресурс не вызывает ложную startup ошибку. Backend/auth не блокируют показ окна.

Журнал prepared-update-attempt.json ограничивает попытки, но не заменяет штатный кэш electron-updater. Перед автоустановкой проверяются safeShutdown, отсутствие media owner, реальная NSIS installation, publisher текущего exe/installer, новая версия и совпадение повторно проверенных metadata. Одна автоматическая попытка на installedVersion/artifact; успешный restart подтверждается реальным app.getVersion(). При отказе запускается рабочая версия; повтор возможен явно с подтверждением. Dev и win-unpacked не устанавливают update. Production policy без утверждённого signing/feed не включать.

Команды: npm run dev:desktop (порт 3000 свободен), npm run dev:desktop:hmr для явного HMR; npm run pack:desktop → release/win-unpacked/Zvonok.exe; npm run dist:desktop → release installer. Проверенная изолированная QA сборка E6.1 лежит в artifacts/stages/electron-e6-1/final-pass/package-final/win-unpacked/Zvonok.exe и использует локальный E6 стенд, не production.
